# FlexGuard native enterprise monetary ledger — P0 candidate
Use PostgreSQL-only migration 0057 after 0053–0054. PR #1's overlapping 0053–0056 numbering and untrusted client monetary values are not blindly merged. Native feature flag RTICORE_FLEXGUARD_ENTERPRISE_ENABLED=1 is for certified staging only; legacy POST is closed when active. An already independently approved, scoped wallet with zero legacy events is required; historical wallets require source reconciliation and approved migration design. No automatic opening balance.
Purchases/top-up use approved and fully paid project invoice net of VAT and require independent approved CFO/controller with sufficient limit. Exact integer cents per credit, no rounding drift; non-divisible invoices require review. Lot expiry is contract end; distinct purchases can use different rates. Reservation, release, consumption, expiry and signed adjustment post only through maker/checker. Consumption requires original accepted milestone evidence and a reservation source; currently one consumption per milestone. Positive adjustment only restores a prior negative adjustment, capped at original units; discretionary credits/refund/carry-forward need separate product policy. Negative adjustment and expiry retain monetary evidence for accounting policy review; never auto-recognize breakage.
Transactional wallet row lock serializes approved mutations; immutable ledger, lots and terminal requests; unique invoice, request key and consumption milestone. Legacy DB trigger rejects writes on enrolled wallet. Purchase, consumption, expiry and adjustment emit hashed Finance outbox event in the same transaction. Outbox is NOT journal posting or acknowledgement. Two new outbound-only policy-review types; external inbound contract unchanged. Full Finance mapping, independent journal approval/posting, historical business reconciliation, access/runtime privilege hardening, CI and UAT are separate release gates. No production migration or feature enablement.

0058 adds Finance receiver: approved posting rule, immutable event-to-journal link, purchase reconciliation against existing posted AR invoice journal (never duplicate liability), and automatic creation of **draft only** journals for consumption/expiry/adjustment after original purchase acknowledgement. Expiry and signed adjustment require event-specific independently approved accounting rules; credit expiry alone never recognizes revenue. Acknowledgement requires independently posted matching journal and separately scoped approver. The Finance release gate remains intact; no automatic posting.
