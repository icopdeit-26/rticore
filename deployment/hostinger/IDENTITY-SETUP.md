# Independent identity gateway — staging templates only
Use separate Keycloak PostgreSQL database and credentials, TLS hostname, no public admin console. Import realm template after replacing example.invalid hosts. Create confidential proxy client secret and configure OAUTH2_PROXY_CLIENT_SECRET and OAUTH2_PROXY_COOKIE_SECRET outside git. Set RTICORE_OIDC_ISSUER, RTICORE_OIDC_CLIENT_ID and RTICORE_OIDC_AUDIENCE to match. Require Keycloak browser flow MFA (OTP or WebAuthn) for every enrolled user; the realm template alone does NOT enforce MFA. Disable untrusted email changes and verify existing account ownership before enrollment. Bind Node and proxy to loopback. Nginx overwrites incoming token header; only signed access token from auth_request is forwarded. Test valid session, anonymous denial, forged header, expired token, refresh cookies, CSRF, logout and direct-origin access. Nginx 401 behavior and refreshed/split cookies require staging browser validation. Proxy logout alone does not revoke IdP sessions; WP05 remains open. Do not deploy or activate Finance until security and operational gates pass. Templates are uninstalled and unvalidated against actual server versions.

## Batch 03 session controls
Set RTICORE_PUBLIC_ORIGIN to exact HTTPS app origin, RTICORE_OIDC_CLIENT_SECRET to the confidential client secret (minimum 32 characters), and keep both server-side. API mutation requires matching Origin; integrations without browser Origin need a separate reviewed machine-auth route. Each verified access token is introspected with Keycloak, with no positive caching; inactive tokens or IdP failure deny access. Realm template adds required password + OTP executions; validate import and enrollment on actual Keycloak, disable alternative grants and broker flows, verify no password-only session works. OAuth2 Proxy backend logout calls Keycloak end-session with ID token; verify installed version, real logout and replay denial before release. Existing browser logout remains proxy sign_out; global IdP logout and revocation are not certified until live tests. No deployment authorization.

## MFA enforcement gate (native Hostinger)
The API now rejects access tokens unless the signed `acr` claim is exactly `2`. Import the realm into a fresh staging Keycloak 26.x instance and verify the LoA subflow actually records level 2 after both password and OTP, that the default `acr` client scope emits it in the access token, and that lower-level or missing claims fail closed. Do not replace the claim with a hardcoded mapper. Verify minimum/default ACR settings on the installed version. Disable offline tokens and alternative grants; provision each existing verified user with CONFIGURE_TOTP using the administrator-controlled enrollment process. Test first enrollment, wrong OTP, password-only denial, token refresh (including refresh rotation), concurrent requests, expired token, disabled member, IdP outage, logout and revoked-token replay. Use a dedicated staging environment; never import over an existing realm without backup and reviewed migration. Release only after actual browser and API evidence, plus verified loopback and proxy TLS. This change does not provision Hostinger or claim a live deployment.
