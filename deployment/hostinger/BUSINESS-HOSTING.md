# RTICORE Business Web Hosting — candidate (HOLD until live acceptance)
The existing hostinger runtime now accepts explicit RTICORE_AUTH_MODE=business. No Keycloak, OAuth2 Proxy, Redis, custom Nginx, root access, Cloudflare or systemd is required in that mode. The legacy VPS OIDC profile remains separate and is not a fallback. OpenAI-only policy and strict external PostgreSQL TLS continue to apply.
## Deployment
1. Use a dedicated staging site and separate external PostgreSQL database. Verify actual Node.js 22 support, start command, dynamic PORT, HTTPS and outbound PostgreSQL/OpenAI reachability for the chosen Business plan. Use exact reviewed commit and npm ci / npm run build / npm start. Set business.env.example values through protected application environment. Do not store real keys in Git or logs. Preserve existing AI and document keys during data migration; generate a separate random 32-byte base64 IAM key and store a protected backup.
2. Back up and restore existing business data in an isolated database. Review and apply PostgreSQL migrations in order including Finance 0053–0054, native FlexGuard 0057–0061, IAM 0062, product and PSA 0063–0066 (deployment/hostinger/migrations). Use migration-owner connection, never request-time DDL. Also apply the separate CAMS native PostgreSQL stream 0053–0054 under sql/native-postgres, without renumbering. Verify grants: application role can use only required tables/sequences, not create/alter schema, own application objects, assume privileged roles or truncate application tables; operator and cron roles have separately reviewed least privileges.
3. Provision active RTICORE members with existing RBAC controls. On a trusted operator workstation using protected configuration, run npm run iam:invite -- approved@example.com. The one-time token expires in 30 minutes. Deliver privately after identity verification. The member activates on /login, sets a unique password and enters a TOTP code from their authenticator. Use a different code at next login. No public registration, password-only access, local user selection or OIDC header bypass in business mode.
4. Independently enroll at least two administrators; run node --experimental-strip-types scripts/hostinger-preflight.mjs. The staging UAT must test password-only denial, forged cookie/headers, CSRF, one-time invite, concurrent TOTP replay, rate limit, logout, idle and absolute timeout, member disable and role/entity isolation. Do not use production user data or credentials in CI.
5. Recovery is operator-controlled: independently verify identity and approval, run npm run iam:revoke -- approved@example.com REVOKE_ALL_SESSIONS_AND_MFA, then issue a fresh invitation. No self-service password reset or recovery code implemented yet. Review audit records and ensure at least two admins remain enrolled. All linked sessions are deleted atomically with credential revocation.
6. Use Hostinger Cron Jobs for bounded processes, not permanent workers. Configure a separate private environment and enable only after testing. npm run cron:iam prunes at most 500 expired/idle sessions per invocation; npm run cron:sales retains existing transactional PostgreSQL scheduler. Validate exact cron working directory, node path and protected environment injection on Hostinger. Never include credentials in cron command text. Transactional outbox dispatch and CAMSRTI reconciliation require additional acceptance.
## Security choices and limits
Node built-in scrypt (N=32768,r=8,p=3), AES-256-GCM protected TOTP seed bound to email, 256-bit opaque sessions stored as SHA-256 hashes, Secure HttpOnly SameSite=Strict cookie, exact Origin mutation checks, 30-minute idle/8-hour absolute TTL. scrypt selected to avoid native addon compatibility risk; load test CPU and memory and tune only after security review. TOTP replay is prevented by an atomic last-step update in the same PostgreSQL statement as session creation/audit. Rate limit is fixed-window bounded buckets (5/15 min per identifier bucket and global 120/min), with possible collisions and denial-of-service tradeoff. Add edge/request concurrency limits if supported. Review failed-attempt monitoring, password breach checks, administrator recovery dual control, browser security headers and page protection before release. CI test fixture validates SQL using isolated PostgreSQL only; real Hosting UAT remains mandatory. No production migration, credentials, enrollment, merge or deployment is claimed.
